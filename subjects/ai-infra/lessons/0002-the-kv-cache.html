The KV cache

Work out how many conversations a GPU can serve at once, and how long they can be.

Why this matters. In lesson 1 the weights decided whether a model can run. The KV cache decides how many users it can serve, which is what an inference company actually sells. Most serving-engine features (vLLM's PagedAttention, prefix caching, KV offloading) exist to manage this one block of memory.

Warm-up: from last time

A 32B model in fp8: the weights take about…

32 billion × 1 byte = 32 GB.

Why must the weights live in GPU memory rather than CPU RAM?

Each new token reads essentially every weight. GPU memory delivers 3.35 TB/s on an H100; PCIe from CPU RAM is roughly 50× slower, so the GPU would mostly wait.

What the cache is

An LLM writes one token at a time. To choose the next token, a step called attention looks back at every earlier token in the conversation. In each layer, every earlier token gets turned into two lists of numbers: a key and a value.

For a token that's already been processed, its keys and values never change. So instead of recomputing them for the whole conversation on every step, the engine computes them once and stores them: the KV cache. As an engineer you know this pattern: it's memoization. It trades memory for compute, and the memory grows by one entry per token, per conversation.

How big it is

KV per token = 2 × layers × KV heads × head dim × bytes

The 2 is for keys plus values. The other numbers come from the model's config.json. This is the formula from How to Scale Your Model1:

Llama 3.1, bf16LayersKV headsHead dimPer token
8B2328128~130 kB
70B3808128~330 kB

Then multiply out. The shortcut: kB per token × thousands of tokens = MB.

per conversation = KV per token × tokens

conversations at once = free memory ÷ per conversation

Worked example

Llama 3.1 8B in bf16 on one H100 (80 GB):

  1. Weights: 8 × 2 = 16 GB. Free: about 64 GB.
  2. One 8,000-token conversation: 130 kB × 8k = 1,040 MB ≈ 1 GB.
  3. Conversations at once: 64 ÷ 1 ≈ 64.

Now let each conversation be 32k tokens: 4 GB each, so only 16 at once. Context length and number of users trade off directly. That's the core sizing tension in LLM serving.

Treat these as upper bounds. Engines also need working memory for the computation itself, so real capacity is lower; How to Scale Your Model suggests real numbers are often around half the clean estimate1.

Why "KV heads" is in the formula

Llama 3 70B has 64 attention heads but only 8 KV heads3: groups of heads share one set of keys and values. This is called grouped-query attention (GQA), and it shrinks the KV cache "by a factor of the Q:KV ratio"1, here 8×. Without it, one 32k-token conversation on the 70B model would need about 86 GB, more than a whole H100. Model architecture choices are infrastructure choices.

A preview of lesson 4: the vLLM team found that serving systems before vLLM wasted 60–80% of this memory through fragmentation and over-reservation4. Fixing that is how vLLM got its name.

Practice

1. What does the KV cache store?

The attention keys and values of every token so far, per layer, so they aren't recomputed at each step.

2. Llama 3.1 8B uses ~130 kB per token. One 8,000-token conversation needs about…

130 kB × 8k = 1,040 MB ≈ 1 GB.

3. Every conversation doubles in length. The number you can serve at once…

Each conversation's cache doubles, so the same free memory holds half as many.

4. Which does not change the KV cache per token?

More users means more tokens in total, but each token's cache size is fixed by layers, KV heads, head dim and precision.

5. A 70B model in fp8 on two H100s (160 GB). Its KV cache is ~5.3 GB per 32k-token conversation. How many of those fit at once?

Weights 70 × 1 = 70 GB, leaving ~90 GB. 90 ÷ 5.3 ≈ 17, as an upper bound.
