Will it fit?

Estimate how much GPU memory a model's weights need, in your head, in five seconds.

Why this first. Whatever the company sells (an inference API, a GPU cloud, a training platform), the first question about a model is the same: how much memory does it need, and on how many GPUs? It decides cost, latency and architecture. Engineers at these startups do this arithmetic constantly, and interviewers expect it.

A model is a big file of numbers

An LLM is mostly its parameters (also called weights): billions of numbers learned during training. The "70B" in Llama 3 70B means 70 billion parameters. To serve the model, all of them must sit in the GPU's own memory, called HBM2, so they can be read for every token generated.

Each parameter is stored at some precision (the number format, or dtype), and that sets how many bytes it takes:

PrecisionBytes / paramWhere you'll see it
fp324Training maths; rarely for serving
bf162The default for released models
fp8 / int81Quantized serving
int40.5Aggressive quantization

Storing a model at fewer bits than it was trained at is called quantization. It shrinks memory, sometimes at a small cost in quality.

The one formula

weight memory = parameters × bytes per parameter

billions of params × bytes = GB

The shortcut works because a billion bytes is a gigabyte. So a 70B model in bf16 is 70 × 2 = 140 GB; in int8, 70 GB; in int4, 35 GB. Those are exactly the figures in Google's How to Scale Your Model1.

Now compare with the GPU. An NVIDIA H100 has 80 GB of memory3; an H200 has 141 GB4. So a 70B model in bf16 does not fit on one H100: you need to split it over several GPUs, quantize it, or both.

The catch: weights are not the whole bill

While generating, the model also keeps a KV cache: stored intermediate values for every token in every active conversation. It grows with context length and with the number of simultaneous users. For Llama 3 70B it is about 160 kB per token in int8, which is about 5.3 GB for one 32k-token conversation1. So "the weights fit" means "it can run", not "it can serve many users". The memory left after the weights is your KV-cache budget. That's the next lesson.

Real-world check: Llama 3.1 405B in fp8 is about 405 GB of weights. vLLM serves it on a single node of 8 H100s (640 GB), leaving the rest for KV cache5.

Pedantic aside: GPU specs use GB (109 bytes) loosely; tools often report GiB (230). The 7% difference doesn't matter for estimates.

Practice: recall, don't reread

Answer from memory. Scroll back up only after you've committed to an answer.

1. Llama 3 8B in bf16: the weights take about…

8 billion × 2 bytes = 16 GB. It fits easily on one H100.

2. A 70B model in bf16 on one H100 (80 GB)…

70 × 2 = 140 GB, well over 80 GB. You'd need at least two H100s, or a quantized version.

3. The same 70B model quantized to int4. The weights take about…

int4 is half a byte per parameter: 70 × 0.5 = 35 GB. Now it fits on one H100 with room to spare.

4. Why leave GPU memory free beyond the weights?

Every token in every active conversation adds to the KV cache. Free memory = how many users and how much context you can serve.

5. Which change halves the weight memory?

2 bytes → 1 byte per parameter. A second GPU splits the weights across two devices but the total stays the same; context length affects the KV cache, not the weights.

6. Llama 3.1 405B in fp8. The fewest H100s that can hold just the weights?

405 GB ÷ 80 GB = 5.06, so 6. In practice it runs on a full 8-GPU node: servers come in 8s, and the spare memory goes to the KV cache.

Then build speed. Do five of these. Aim to answer each in under ten seconds.

Your win: for any model, you can now say how much memory its weights need, and whether they fit on an H100 or H200.
